■FAQ/DocTestの実行方法と失敗の報告方法（開発者向け）

DocTestは、マニュアルに書かれたサンプルコードを実際に実行して、書かれている表示結果のとおりに動くかを自動で確認する仕組みです。このページでは、開発者向けに、DocTestの実行方法と、失敗したときの切り分け方・報告の書き方をまとめます。

一般向けの説明は [[FAQ/ランタイムについて]]、バージョンの確認や更新の方法は [[FAQ/各ランタイムのインストールとアップデート]] をご覧ください。

●DocTestの書き方（おさらい）

マニュアルのテキストファイル（`.txt`）の中で、`{{{#nako3` と `}}}` で囲んだブロックに `### 表示結果:` を書くと、そのブロックがDocTestの対象になります。

{{{#nako3
10 + 5を表示。
### 表示結果: 15
}}}

表示結果が複数行になる場合は、2行目以降も `### ` に続けて書きます。表示結果の見出しがないブロックは、説明用のコードとして扱われ、DocTestの対象にはなりません。

▲ラベルの種類

見出しの文言（ラベル）によって、どのランタイム向けのサンプルなのかを書き分けます。

- `### 表示結果:` --- 全ランタイム共通の仕様を確認するサンプルです。公式実装の cnako3 で動くことが前提で、gonako / lnako でも同じ結果になることを期待します
- `### WEB表示結果:` --- ブラウザ版（wnako）専用のサンプルです。CUI版のランナーでは自動的にスキップ（省略）されます
- `### GO表示結果:` --- gonako 独自の命令のサンプルです。本家にはない命令なので、`表示結果` とは書き分けます
- `### lnako表示結果:` --- lnako 独自の命令のサンプルです（`data/lnako`、`data/lnako_node`、`data/lnako_lowlevel` 以下で使います）

なお、ラベルは「英数字の接頭辞＋表示結果」という形式なら自由に付けられます。なでしこ3go のテストデータでは lnako 用に `L表示結果` という短いラベルも使われています。ラベル名そのものに意味はなく、実行時に `--label` で指定したものだけが対象になります。**ラベルを書き間違えると対象が0件になり、「対象のサンプルコードがありません」と表示されます。これは成功ではありません**ので、件数を必ず確認してください。

●一番大事なこと：「ランナー」「ランタイム」「ラベル」は別物です

DocTestの実行には、独立した3つの要素があります。失敗を報告するときは、この3つを混同しないでください。

- **ランナー** --- サンプルを抽出して実行・照合する道具そのもの（例: `gonako doctest`、nadesiko3 の `batch/doctest.mjs`）
- **ランタイム** --- サンプルコードを実際に実行する処理系（cnako3 / gonako の内蔵VM / lnako）。ランナーの `--runtime` オプションで差し替えられます
- **ラベル** --- 対象にする見出しの種類（`表示結果` など）

たとえば「`gonako doctest` で失敗した」という報告だけでは、gonako の内蔵VMで実行したのか、`--runtime=cnako3` で cnako3 に実行させたのかが分からず、どちらの実装の問題なのか切り分けられません。過去に、内蔵VMでの失敗だけを見て「どの実装の問題か曖昧」な報告になった事例（nadesiko3doc Issue #125）があるため、報告の際は後述のテンプレートを使ってください。

●ランナーごとの実行方法

▲(1) gonako doctest（Go版ランナー）

最も手軽なランナーです。`--runtime` を省略すると gonako の内蔵VMで実行します。

{{{
# 対象を指定して実行（ファイルでもフォルダでも可）
gonako doctest --label=表示結果 data/文法

# 失敗の詳細を全件表示（既定は10件まで）
gonako doctest --label=表示結果 --max 0 data/文法

# gonako独自命令のサンプル
gonako doctest --label=GO表示結果 data/gonako

# 失敗をJSONで出力（AIやスクリプトで処理しやすい形式）
gonako doctest --label=表示結果 --json=result.json data/文法
}}}

外部ランタイムで実行するには `--runtime` を使います。相手がサブコマンドを必要とする場合は `--subcommand` も付けます。

{{{
# cnako3 で実行（cnako3 はファイルパスを直接受け取る）
gonako doctest --runtime=cnako3 --label=表示結果 data/文法

# lnako で実行（lnako は `lnako run ファイル` の形なので run が必要）
gonako doctest --runtime=lnako --subcommand=run --label=表示結果 data/文法

# lnako独自命令のサンプルを lnako で実行
gonako doctest --runtime=lnako --subcommand=run --label=lnako表示結果 data/lnako data/lnako_node data/lnako_lowlevel
}}}

知っておくべき仕様は次のとおりです。

- 終了コードは、全件成功なら 0、失敗があれば 1、引数の誤りなどは 2 です。CIではこの終了コードで判定できます
- 外部ランタイムで実行する場合、サンプル1件ごとに10秒で打ち切ります。時間切れは失敗として報告され、後続のサンプルは続けて実行されます
- `--runtime` を指定したときは、内蔵VM向けの省略処理（ブラウザ専用命令のスキップなど）は適用されません。相手ランタイムが対応していればそのまま実行されます
- `--runtime` に渡せるのは実行ファイル1つだけです。`node src/cnako3.mjs` のように追加の引数が必要な場合は、ラッパースクリプトを用意してそれを渡してください
- パスを省略した場合の対象は、なでしこ3go リポジトリ内の `manual/plugin_system`、`manual/gonako`、`testdata/doctest` です。マニュアル（nadesiko3doc）を対象にするときは、必ずパスを指定してください

▲(2) nadesiko3 の DocTest（公式リポジトリのランナー）

公式リポジトリ（kujirahand/nadesiko3）には、DocTest が2実装あります。詳しい仕様は nadesiko3 リポジトリの `doc/doctest.md` が正本です。

{{{
# JS版（batch/doctest.mjs）: NakoCompiler の内部で実行するので高速。cnako3 専用
npm run doctest
npm run doctest -- manual/plugin_system/表示.txt

# テストとして実行（npm run test:node にも含まれます）
npm run test:doctest

# なでしこ版（batch/doctest.nako3）: ランタイムを切り替えられる
npm run doctest:nako3
npm run doctest:nako3 -- --runtime gonako
npm run doctest:nako3 -- --runtime lnako --subcommand run --label lnako表示結果
npm run doctest:nako3 -- --json=result.json
}}}

注意点は次のとおりです。

- ここでいう `manual` は、nadesiko3 リポジトリ内に作るシンボリックリンクで、nadesiko3doc の `data` フォルダを指します。リンクがない環境では、マニュアル分のテストはスキップされます（失敗にはなりません。「何件実行されたか」を必ず確認してください）
- なでしこ版は、サンプルを別プロセスで実行します。実行には POSIX のシェル（`/bin/sh`）を使うため、macOS / Linux での利用を想定しています
- 環境変数 `NAKO3_DOCTEST_RUNTIME` で `--runtime` の既定値を指定できます

▲(3) wnako のブラウザDocTest

`### WEB表示結果:` のサンプルは、Playwright + Chromium で実際のブラウザ上で実行して確認します。

{{{
cd test-browser
npm run test:doctest
}}}

▲(4) gonako-gui のエディタ

gonako-gui のエディタで文法チェックを行うと、開いているバッファに DocTest があれば続けて実行されます。ちょっとした確認には便利ですが、まとまった検証はコマンドラインのランナーで行ってください。

●失敗したときの切り分け手順（三角測量）

DocTest が失敗しただけでは、それが「実装のバグ」なのか「マニュアルの誤り」なのかは分かりません。次の手順で、同じサンプルを3つのランタイムで実行して比べてください。これが切り分けの基本です。

{{{
# 1. 公式実装 cnako3 で実行する（仕様の基準）
gonako doctest --runtime=cnako3 --label=表示結果 --max 0 <対象>

# 2. gonako の内蔵VMで実行する
gonako doctest --label=表示結果 --max 0 <対象>

# 3. lnako で実行する
gonako doctest --runtime=lnako --subcommand=run --label=表示結果 --max 0 <対象>
}}}

結果の読み方は次のとおりです。

- cnako3 が成功し、gonako だけが失敗 → gonako の未対応・バグの可能性が高いです。Issue は nadesiko3go へ立ててください
- cnako3 も同じように失敗 → マニュアルの期待値かサンプルコードの誤り、あるいは cnako3 自体の仕様・バグです。まず nadesiko3doc 側で期待値とサンプルを見直し、仕様の問題なら nadesiko3 へ Issue を立ててください
- cnako3 と gonako が成功し、lnako だけが失敗 → lnako 側の問題候補ですが、**lnako の互換基準バージョンを確認してから判断してください**（下記）
- 3つとも失敗し、エラー内容もバラバラ → サンプル自体が環境依存（ファイル・ネットワーク・実行のたびに変わる値など）の可能性があります。その場合は `### 表示結果:` を外し、期待値を `# → 値` のコメント形式に変えることを検討してください
- `GO表示結果` / `lnako表示結果` のサンプルは、そのランタイムでだけ判定してください。他のランタイムで失敗しても問題ではありません

▲lnako の互換基準バージョンに注意

lnako の互換基準は、なでしこ3 v3.7.24 です（`lnako compat report` で確認できます）。そのため、v3.7.24 より後に追加された文法は、lnako で失敗しても「バグ」とは限りません。2026-11-25 の実測では、コミット済みの `data/文法` の DocTest 31件が、cnako3（v3.8.12）と gonako（v3.8.12）では全件成功した一方、lnako（0.2.5）では13件の成功にとどまり、`もし式` や範囲アクセス（`A[0…3]`）など新しい文法のサンプルが失敗しました。これは基準バージョンの差として報告するのが正確です。

●報告の書き方（テンプレート）

DocTest の失敗を Issue で報告するときは、以下の項目を必ず書いてください。特に **バージョンは必須** です。バージョンには「ランタイム自身のバージョン」と「`ナデシコバージョン` 定数の値」の2種類があり、実装によって数値が違うため、両方を書いてください（詳しくは [[FAQ/各ランタイムのインストールとアップデート]]）。

{{{
## 実行環境
- OS / CPU: (例: macOS 15 / arm64、Ubuntu 24.04 / x86_64)
- ランナー: (例: gonako doctest / nadesiko3 の npm run doctest)
- 対象マニュアルのコミット: (nadesiko3doc のコミットハッシュ。
  未コミットの変更に対する結果は、他の人が再現できないので必ず明記)

## バージョン（必須）
- cnako3: cnako3 --version の出力 / ナデシコバージョン定数の値
- gonako: gonako version の出力 / ナデシコバージョン定数の値 /
  GONAKOバージョン定数の値
- lnako: lnako --version の出力 / ナデシコバージョン定数の値（＝互換基準）

## 実行コマンド（そのままコピー＆ペーストできる形で）
gonako doctest --label=表示結果 --max 0 data/文法

## 結果
- 件数: 全○件中 成功○件 / 失敗○件 / 省略○件
- 失敗したファイルと行: (例: data/文法/もし式.txt:20)
- 失敗したサンプルごとに、コード・期待値・実際の値・エラー内容

## 切り分け結果
- cnako3 では: 成功 / 失敗（失敗なら内容）
- gonako では: 成功 / 失敗（失敗なら内容）
- lnako では: 成功 / 失敗（失敗なら内容。互換基準バージョンとの関係も）
- 見立て: どの実装の問題だと思うか、その根拠
}}}

報告の際の注意点は次のとおりです。

- バージョン確認を手抜きしないでください。「最新版で確認した」ではなく、コマンドの出力そのものを貼るのが確実です。古いバイナリが PATH の先に残っていて、古い版で検証してしまう事故が起きがちです。心配な場合は、先に [[FAQ/各ランタイムのインストールとアップデート]] のスクリプトで最新版に揃えてから実行してください
- 失敗の全件が要る場合は `--max 0` を付け、可能なら `--json` の出力ファイルも添付してください。件数の多い報告は JSON があると、受け取る側（人でもAIでも）が処理しやすくなります
- 「○件中○件失敗」という要約だけでなく、失敗したファイル名と行番号の一覧を必ず添えてください。要約だけでは、受け取った人が再現できません
- 期待値の誤りだったのか、実装の問題なのか、切り分けが済んでいない場合は、その旨を正直に書いてください。切り分け前の報告は、そのこと自体を明記すれば十分に役立ちます
